# Requirements Document

## Introduction

Pantry derives a shopping list from inventory shortfalls and manual additions, and already exposes an "Export to cart" action backed by a `CartExporter` seam that is currently wired to a no-op implementation. This feature replaces that no-op with real provisioning of the shopping list into an external grocery service, so that a single pantry user can hand the current shopping list to a grocery provider and complete checkout in that provider's own app or website.

The feature is specified provider-agnostically from the first requirement, with Kroger as the first and currently only concrete adapter.

### Why the provider abstraction is foundational rather than added later

Grocery services differ so radically from one another that a uniform single-method exporter interface is the wrong shape. One service issues OAuth2 tokens for a consumer account; another authenticates with a static API key; another needs no account at all. One accepts a server-to-server cart write; another can only hand the user off to its own web UI to finish the order. One reports the result of each line; another reports one result for a whole request; another reports nothing at all. One identifies a product by a value Pantry can derive from the barcode it already stores; another requires a catalog lookup before anything can be requested.

A single interface that assumes the union of those behaviors forces every adapter to lie about what it can do, and a single interface that assumes the intersection can express almost nothing. This specification therefore treats a **provider as a record of declared capabilities**, and specifies a single **Provisioning_Engine** that reads those capabilities and degrades its behavior accordingly. The engine never invokes an operation that a provider did not declare.

Capability declaration is also how provider limitations are represented. A limitation is data, not prose: Kroger's cart operation supports adding items only and exposes no reading, updating, or removal of cart contents, which this document records as a Mutation_Capability of `add_only` on the Kroger adapter rather than as a caveat attached to a requirement. Widening a limitation later is a change to a declared capability value, not a change to the engine.

### Why the abstraction is proven by a fake provider rather than by a second live provider

Provider-agnostic structure is only credible if something other than the first adapter exercises it. A second live integration is not available: some major grocery retailers publish only seller-side marketplace APIs, with no consumer-facing endpoint that writes to a shopper's own cart, so such a service cannot be a peer provider of Kroger under this feature at all. The abstraction is therefore proven by a **Fake_Provider whose capabilities are configurable**, driven by the shared Contract_Suite of Requirement 16, so that capability combinations Kroger does not exercise are still covered by tests that need no network access and no credentials.

### Why the export timestamp is replaced by a per-provider ledger

The earlier shape of this feature tracked provisioning progress as a single global "last export time". That shape carried a defect: the timestamp advanced whenever one or more items succeeded, which erased the consumed-units basis of the items that had **failed** in the same operation, so those items silently disappeared from the shopping list. With more than one provider the shape is definitively wrong, because there is no single last export time to hold.

This document replaces that timestamp with a **Fulfillment_Ledger**: for each pair of provider and pantry product, the quantity Pantry believes it has already requested, and the boundary from which that belief is measured. A ledger entry advances only for a pantry product whose provisioning was confirmed, which removes the silent-loss defect by construction rather than patching it, and makes provisioning idempotent in both replenishment modes.

### Scope

- **Single pantry user.** One set of provider connections belongs to the one pantry user (`user-1`). Per-user connection management is out of scope.
- **One-way push.** Items flow from the pantry shopping list into a provider. Provider cart contents are never read back, and Pantry performs no checkout.
- **No interactive product mapping.** A pantry item whose Provider_Product_Identity cannot be resolved is skipped and reported. Building a search-and-pick UI to permanently map pantry products to provider products is out of scope.
- **Per-product replenishment mode.** Each pantry product carries a Replenishment_Mode: `target` restocks up to the product's recorded target quantity, and `replenish` buys back the units consumed since the product's Ledger_Boundary for the chosen provider. `target` is the default.
- **User-adjustable quantities.** Every computed quantity can be overridden by hand before provisioning, including an override of 0 that leaves that entry out of the operation entirely.
- **No shopping list mutation.** Provisioning does not mark items purchased or remove them. The only list state a Provision_Operation changes is the Adjusted_Quantity of an entry whose provisioning was confirmed, which is cleared so that the next computed quantity is shown fresh.

### Validated Assumptions

The aspects of the Kroger Public API that this feature previously recorded as unconfirmed were verified against the [Kroger Cart API OpenAPI document, version 1.2.3](https://developer.kroger.com/api-products/api/cart-api-public), the Kroger Products API OpenAPI document, and the Kroger Authorization Endpoints OpenAPI document, all retrieved from the Kroger developer portal's own contract endpoints. The outcomes are recorded here because they fix values that Requirement 17 declares.

- **Scope string — confirmed.** The scope string is `cart.basic:write`, declared by the Cart API security scheme as granting write access to a customer's cart. Requirement 17 states that value as confirmed rather than assumed.
- **Confirmation granularity — confirmed correct, not merely conservative.** A successful cart-add answers `204` with no response body and no declared response schema, so the response carries no per-item results, and a rejection carries one error object for the whole request rather than a per-item array. The Kroger Confirmation_Capability of `per_request` that Requirement 17 declares is therefore correct on the evidence, not a conservative reading awaiting revision. The practical consequence, stated in Requirement 17, is that one malformed Provision_Line rejects its whole Provision_Request.
- **Mutation scope — confirmed.** The Cart API document declares exactly one path and one method, `PUT /v1/cart/add`, and exposes no operation that reads, updates, or removes cart contents, which confirms the Kroger Mutation_Capability of `add_only`.
- **Product identifier — refuted.** The assumption that Kroger's 13-digit product identifier is the zero-padded 12-digit UPC is wrong. The Products API document states that the identifier is the 13-digit `productId` and that the check digit is omitted when converting from a barcode, so the identifier is the GTIN with its check digit discarded and the remaining data digits left-padded with `0` to 13 characters. That rule was confirmed arithmetically against four published Kroger identifiers — `0001111060903`, `0001111041700`, `0001200016268`, and `0001111041600` — none of which is a valid zero-padded UPC-A or a valid EAN-13, and every one of which the check-digit-discarding rule reproduces. Requirement 17 and the Normalized_Barcode definition state the corrected rule.
- **Rate limit — newly confirmed.** The Cart API documents a hard quota of 5,000 calls per day. This bears on Requirement 13, whose attempt limits, retry caps, and backoff waits remain Pantry's own policy values rather than published provider limits, but which now has one published Kroger limit to respect alongside them.

The UPC-E expansion rule and the check-digit integrity gate that Requirement 17 states were verified against the [GS1 General Specifications, Release 26.0](https://ref.gs1.org/standards/genspecs/), section 5.2.2.4.2 Table 5-7 (decoding a UPC-E barcode) and section 7.9 (check digit calculation).

One question remains open and is recorded rather than silently resolved. Kroger publishes no worked example of converting a 13-digit barcode, so the EAN-13 branch of the rule is an extrapolation from the documented instruction to omit the check digit; every arithmetically verified identifier derives from a 12-digit UPC-A.

One further ambiguity is **decided and its residual accepted**, and is recorded here as an acceptance rather than as an open question. An 8-character barcode is ambiguous between a UPC-E and an EAN-8, which no check digit resolves, so Pantry goes by length and treats such a barcode as a UPC-E under the gates of Requirement 17.6, accepting the rare misread that follows. The consequence is bounded by human review at checkout: the Cart API declares no checkout operation, so the pantry owner completes the purchase in the Kroger app and an unexpected line item can be removed before paying. Requirement 17.18 states the accepted residual.

A 13-character *stored* barcode carries no such ambiguity, because Requirement 5.12 stores every barcode exactly as it appears on the real-world object and never persists a Provider_Product_Identity: a converted value has no path into a barcode of a pantry product, so a stored 13-character barcode is an EAN-13.

## Glossary

### Core terms

- **Pantry**: The complete application, comprising the Go backend and the React frontend.
- **Grocery_Provider**: An external grocery service into which Pantry can request items, identified by a Provider_Identifier and described by exactly one Provider_Capabilities record. Referred to below as a provider.
- **Provider_Identifier**: A stable, lowercase, non-empty string that names one Grocery_Provider and that is used to namespace that provider's configuration, credentials, and Fulfillment_Ledger entries.
- **Provider_Adapter**: The Pantry backend component that implements, for exactly one Grocery_Provider, the operations that provider's Provider_Capabilities declare.
- **Provider_Registry**: The Pantry backend component that holds the Provider_Capabilities record and the Provider_Adapter of every registered Grocery_Provider and that resolves a Provider_Identifier to that pair.
- **Provisioning_Engine**: The provider-agnostic Pantry backend component that computes Provision_Quantities, resolves Provider_Product_Identities through a Provider_Adapter, submits Provision_Requests, records Provision_Outcomes, and maintains the Fulfillment_Ledger. The Provisioning_Engine is an implementation of the existing `CartExporter` seam.
- **Provider_Capabilities**: A record held for one Grocery_Provider carrying exactly one value for each of the five capability dimensions: Authentication_Capability, Delivery_Capability, Confirmation_Capability, Mutation_Capability, and Product_Identity_Capability.
- **Authentication_Capability**: Exactly one of `none` (the provider accepts requests without a credential), `oauth2_authorization_code` (the provider issues tokens through an OAuth2 authorization-code flow against a user account), or `api_key` (the provider accepts a static credential supplied through Pantry configuration).
- **Delivery_Capability**: Exactly one of `server_push` (the Pantry backend submits Provision_Requests directly to the provider) or `client_handoff` (Pantry produces a handoff artifact that the pantry owner completes in the provider's own user interface).
- **Confirmation_Capability**: Exactly one of `per_line` (the provider reports an outcome for each Provision_Line), `per_request` (the provider reports one outcome for a whole Provision_Request), or `none` (the provider reports no outcome).
- **Mutation_Capability**: Exactly one of `add_only` (the provider accepts additions and exposes no reading, updating, or removal), `add_and_update` (the provider accepts additions and quantity updates), or `full` (the provider accepts additions, quantity updates, and removals).
- **Product_Identity_Capability**: Exactly one of `derived` (a Provider_Product_Identity is a pure function of a pantry barcode and needs no provider call) or `looked_up` (a Provider_Product_Identity requires a call to the provider).
- **Provider_Product_Identity**: The non-empty string by which one Grocery_Provider identifies one pantry product within that provider's own catalog.
- **Provider_Connection_Record**: The persisted row holding the connection state and, where the Authentication_Capability requires credentials, the credentials of exactly one Grocery_Provider for the pantry user. Pantry holds at most one Provider_Connection_Record per Provider_Identifier.
- **Connection_State**: One of exactly four values describing one Provider_Connection_Record: `not_required` (the provider's Authentication_Capability is `none`), `connected` (a usable credential is stored or configured), `reauth_required` (a stored credential was rejected by the provider), or `disconnected` (no credential is stored).
- **Provider_Credentials**: The values that one Grocery_Provider's Authentication_Capability requires Pantry to read from its environment at startup, namespaced by that provider's Provider_Identifier.
- **Credentials_Configured**: The condition, evaluated per Grocery_Provider, in which every Provider_Credentials value that provider's Authentication_Capability requires is present in the environment and the environment variable that disables that provider is not set to `true`. A provider whose Authentication_Capability is `none` is Credentials_Configured whenever the environment variable that disables that provider is not set to `true`.
- **Authorization_State**: The opaque state value that a Provider_Adapter whose Authentication_Capability is `oauth2_authorization_code` generates for an authorization URL and persists, together with the time of generation, in that provider's Provider_Connection_Record. An Authorization_State is valid for 600 seconds after that generation time, and is discarded once a callback consumes it or the callback is rejected for an error parameter or expiry.

### Shopping list and quantity terms

- **Shopping_List_Page**: The Pantry frontend page that displays the shopping list and hosts the provisioning and provider-connection controls.
- **Shopping_List_Entry**: One line of the shopping list as returned by a shopping list read, carrying a pantry item identifier, a Computed_Quantity, any Adjusted_Quantity recorded against that line for the Target_Provider, and a source of either `auto` (inventory-derived restocking) or `manual` (manual addition).
- **Target_Provider**: The single Grocery_Provider for which one shopping list read or one Provision_Operation computes quantities. Where exactly one registered provider is Credentials_Configured, that provider is the Target_Provider of a read that names none.
- **Replenishment_Mode**: A setting held per pantry product, equal to exactly one of `target` or `replenish`, that selects how Pantry computes the Computed_Quantity for that product. A pantry product for which no Replenishment_Mode has been recorded holds a Replenishment_Mode of `target`.
- **Target_Shortfall**: For one pantry product, the target quantity recorded for that product minus the count of inventory instances currently held for that product.
- **Fulfillment_Ledger**: The persisted set of Fulfillment_Ledger_Entries, holding what Pantry believes it has already requested from each Grocery_Provider for each pantry product.
- **Fulfillment_Ledger_Entry**: One record of the Fulfillment_Ledger, keyed by the pair of a Provider_Identifier and a pantry product, carrying a Requested_Quantity and a Ledger_Boundary. Where no Fulfillment_Ledger_Entry exists for a pair, the Requested_Quantity of that pair is 0 and the Ledger_Boundary of that pair precedes every consumption event Pantry holds.
- **Requested_Quantity**: The integer of 0 or greater carried by one Fulfillment_Ledger_Entry, being the number of units Pantry believes it has already requested from that provider for that pantry product since that entry's Ledger_Boundary.
- **Ledger_Boundary**: The absolute time carried by one Fulfillment_Ledger_Entry, from which the Consumed_Units of that pair are counted.
- **Consumed_Units**: For one pantry product and one Target_Provider, the number of consumption events recorded for that product whose consumption time falls after the Ledger_Boundary of that pair. Pantry records exactly one consumption event per inventory instance removed from the pantry, so Consumed_Units is a count of individual units.
- **Computed_Quantity**: The quantity Pantry derives for one Shopping_List_Entry and one Target_Provider from the Replenishment_Mode of that entry's pantry product and the Fulfillment_Ledger_Entry of that pair, as specified in Requirement 7.
- **Adjusted_Quantity**: An integer between 0 and 999 inclusive recorded by the pantry owner against the pair of one Shopping_List_Entry and one Target_Provider, to replace that entry's Computed_Quantity for that provider.
- **Provision_Quantity**: The single quantity value that one Shopping_List_Entry contributes to a Provision_Operation, equal to that entry's Adjusted_Quantity for the Target_Provider where one is recorded and to that entry's Computed_Quantity otherwise.

### Provisioning terms

- **Resolved_Item**: A Shopping_List_Entry paired with the Provider_Product_Identity that the Target_Provider's Provider_Adapter resolved for that entry's pantry product, together with that entry's Provision_Quantity. Exactly one Resolved_Item is produced per Shopping_List_Entry for which a Provider_Product_Identity was resolved, even when two entries resolve to the same Provider_Product_Identity.
- **Unresolved_Item**: A Shopping_List_Entry for which the Target_Provider's Provider_Adapter resolved no Provider_Product_Identity.
- **Provision_Line**: A pair of Provider_Product_Identity and quantity, together with any provider-specific line options that the Target_Provider declares, submitted to a provider within one Provision_Request. One Provision_Line is derived from one or more Resolved_Items that share the same Provider_Product_Identity, so a Provision_Request can carry fewer Provision_Lines than the number of Resolved_Items it accounts for.
- **Provision_Batch_Size**: The maximum number of Provision_Lines that Pantry places in one Provision_Request for one Grocery_Provider, held as a per-provider policy value. Provision_Batch_Size is a Pantry policy value and is not a published limit of any provider.
- **Provision_Request**: A single request to one Grocery_Provider carrying between 1 Provision_Line and that provider's Provision_Batch_Size Provision_Lines, and accounting for the Resolved_Items from which those Provision_Lines were derived.
- **Provision_Operation**: A single invocation of the Pantry provisioning endpoint for one Target_Provider.
- **In_Progress_Provision_Operation**: A Provision_Operation for one Target_Provider that Pantry has accepted and that has not yet returned a provisioning outcome or an error.
- **Provision_Outcome**: The result recorded for one Shopping_List_Entry within one Provision_Operation, equal to exactly one of `confirmed` (the provider confirmed the requested units), `failed` (the entry reached no provider, or the provider rejected the request accounting for that entry), or `unknown` (the result of the request accounting for that entry is indeterminate).
- **Handoff_Artifact**: The artifact that Pantry produces for a Grocery_Provider whose Delivery_Capability is `client_handoff`, carrying the Provision_Lines of a Provision_Operation in the form that provider's user interface accepts.
- **Contract_Suite**: The single shared behavioral test suite that every Provider_Adapter is verified against, parameterized by that adapter's Provider_Capabilities.
- **Fake_Provider**: A Grocery_Provider implemented inside the Pantry test code whose Provider_Capabilities are set per test case and which reaches no network.

### Kroger adapter terms

- **Kroger_Provider**: The Grocery_Provider whose Provider_Identifier is `kroger`, backed by the Kroger Public API.
- **Kroger_Adapter**: The Provider_Adapter of the Kroger_Provider.
- **Normalized_Barcode**: A string of exactly 13 characters, every one of which is a digit, derived by the Kroger_Adapter from a pantry barcode by determining the GTIN that barcode carries, discarding that GTIN's check digit, and left-padding the remaining data digits with `0` characters to 13 characters. A UPC-E value is first expanded to its GTIN-12 equivalent, and that expanded value's check digit is the one discarded. A Normalized_Barcode serves unchanged as the Provider_Product_Identity of the Kroger_Provider for that barcode.
- **Cart_Modality**: The Kroger fulfillment channel recorded against one Provision_Line submitted to the Kroger_Provider, either `PICKUP` or `DELIVERY`. The Kroger Public API treats this field as optional and defaults it to `PICKUP`, so Pantry sending a Cart_Modality with every Provision_Line is a deliberate choice to be explicit rather than a requirement of that API.

## Requirements

### Requirement 1: Register Providers and Declare Capabilities

**User Story:** As a Pantry developer, I want every grocery provider to declare what it can do as data, so that the provisioning engine can support unlike providers without a branch per provider and without ever asking a provider for something it cannot do.

#### Acceptance Criteria

1. WHEN the Pantry starts, THE Provider_Registry SHALL hold, for every registered Grocery_Provider, exactly one Provider_Identifier, exactly one Provider_Capabilities record, and exactly one Provider_Adapter.
2. THE Provider_Registry SHALL hold, for every registered Grocery_Provider, exactly one declared value for each of the five capability dimensions Authentication_Capability, Delivery_Capability, Confirmation_Capability, Mutation_Capability, and Product_Identity_Capability.
3. IF a Grocery_Provider is presented for registration with a Provider_Identifier already held by a registered provider, with an empty Provider_Identifier, or with a Provider_Capabilities record that omits a value for any of the five capability dimensions or carries a value outside the permitted values of that dimension, THEN THE Provider_Registry SHALL register no provider from that presentation, SHALL leave every already-registered provider unchanged, and SHALL return an error identifying the rejected Provider_Identifier and the rejected dimension.
4. WHEN the Provisioning_Engine performs any operation against a Grocery_Provider, THE Provisioning_Engine SHALL invoke only those Provider_Adapter operations that the Provider_Capabilities of that provider declare.
5. WHEN a client requests the list of registered Grocery_Providers, THE Pantry SHALL return, for every registered provider, that provider's Provider_Identifier, that provider's display name, that provider's five declared capability values, and whether that provider is Credentials_Configured.
6. IF a client names a Provider_Identifier that the Provider_Registry holds no provider for, THEN THE Pantry SHALL send no request to any Grocery_Provider and SHALL return an error identifying the unknown Provider_Identifier.
7. WHEN the Provisioning_Engine reads a capability value, THE Provisioning_Engine SHALL read that value from the Provider_Capabilities record of the named provider rather than from the Provider_Identifier of that provider, so that adding a provider changes registry data alone.
8. WHILE two or more Grocery_Providers are registered, THE Provisioning_Engine SHALL apply the capability values of the Target_Provider of the current operation and SHALL leave the state of every other registered provider unchanged.

### Requirement 2: Connect an Account per Provider

**User Story:** As the pantry owner, I want to authorize Pantry against each grocery provider that needs an account, so that Pantry can request items on my behalf without me re-entering credentials, and so that a provider needing no account works with no connection step at all.

#### Acceptance Criteria

1. WHERE a Grocery_Provider declares an Authentication_Capability of `none`, THE Pantry SHALL report a Connection_State of `not_required` for that provider, SHALL offer no connection control for that provider, and SHALL permit a Provision_Operation against that provider while that provider is Credentials_Configured.
2. WHERE a Grocery_Provider declares an Authentication_Capability of `api_key`, THE Pantry SHALL read that provider's API key from the environment, SHALL report a Connection_State of `connected` for that provider while that key is present, SHALL report a Connection_State of `disconnected` for that provider while that key is absent, and SHALL run no authorization flow for that provider.
3. WHILE a Grocery_Provider declares an Authentication_Capability of `oauth2_authorization_code` AND that provider is Credentials_Configured, WHEN a client requests the authorization URL of that provider, THE Provider_Adapter of that provider SHALL return an authorization URL containing that provider's configured client identifier, that provider's configured redirect URI, that provider's declared authorization scope, a response type of `code`, and an Authorization_State value that is at least 32 characters long and differs from the state value returned by every previous authorization URL request for that provider.
4. WHEN a Provider_Adapter generates an Authorization_State value, THE Provider_Adapter SHALL persist exactly one Authorization_State value in that provider's Provider_Connection_Record, replacing any Authorization_State value previously persisted for that provider, together with the time at which the value was generated, and SHALL leave the Provider_Connection_Record of every other provider unchanged.
5. WHEN a Grocery_Provider redirects to that provider's configured redirect URI with an authorization code and a state value equal to the Authorization_State value persisted for that provider and generated no more than 600 seconds earlier, THE Provider_Adapter of that provider SHALL exchange the authorization code for an access token and a refresh token, SHALL persist both tokens in that provider's Provider_Connection_Record together with the access token expiry computed as the time the token response was received plus the expiry duration carried by that response, SHALL set that provider's Connection_State to `connected`, and SHALL discard the persisted Authorization_State value so that a repeat callback carrying the same state value is rejected under criterion 6.
6. IF a callback carries no state value, a state value different from the Authorization_State value persisted for that provider, or a state value for which no Authorization_State value is persisted for that provider, THEN THE Provider_Adapter SHALL exchange no authorization code, SHALL leave every Provider_Connection_Record and every Connection_State unchanged, and SHALL return an error identifying the state mismatch.
7. IF a callback carries an authorization code and the Authorization_State value persisted for that provider was generated more than 600 seconds earlier, THEN THE Provider_Adapter SHALL exchange no authorization code, SHALL leave that provider's Provider_Connection_Record and Connection_State unchanged, SHALL discard the persisted Authorization_State value, and SHALL return an error identifying that the authorization attempt expired.
8. IF a callback carries an error parameter in place of an authorization code, THEN THE Provider_Adapter SHALL leave that provider's Provider_Connection_Record and Connection_State unchanged, SHALL discard the persisted Authorization_State value, and SHALL return an error carrying the value of that error parameter.
9. IF a Grocery_Provider rejects an authorization code exchange, THEN THE Provider_Adapter SHALL leave that provider's Provider_Connection_Record and Connection_State unchanged and SHALL return an error identifying the exchange failure.
10. WHEN a second authorization completes for one Grocery_Provider, THE Provider_Adapter SHALL replace the access token, the refresh token, and the access token expiry in that provider's existing Provider_Connection_Record, SHALL leave every Fulfillment_Ledger_Entry unchanged, and SHALL leave exactly one Provider_Connection_Record stored for that provider.
11. IF a client requests the authorization URL of a Grocery_Provider that is not Credentials_Configured, THEN THE Provider_Adapter SHALL return no authorization URL, SHALL persist no Authorization_State value, and SHALL return an error identifying that the named provider is unconfigured.
12. IF a client requests the authorization URL of a Grocery_Provider whose Authentication_Capability is other than `oauth2_authorization_code`, THEN THE Pantry SHALL return no authorization URL and SHALL return an error identifying that the named provider runs no authorization flow.

### Requirement 3: Maintain Provider Credentials

**User Story:** As the pantry owner, I want Pantry to keep each provider credential usable on its own terms, so that provisioning succeeds for weeks without me reconnecting and so that a provider needing no token refresh incurs none.

#### Acceptance Criteria

1. WHERE a Grocery_Provider declares an Authentication_Capability of `none`, THE Provisioning_Engine SHALL attach no credential to a request to that provider and SHALL send no token request for that provider.
2. WHERE a Grocery_Provider declares an Authentication_Capability of `api_key`, THE Provisioning_Engine SHALL attach the configured API key of that provider to every request to that provider and SHALL send no token refresh exchange for that provider.
3. WHILE a Grocery_Provider declares an Authentication_Capability of `oauth2_authorization_code` AND that provider's Connection_State is `connected`, WHEN a valid access token for that provider is requested and the persisted access token expiry of that provider is more than 60 seconds after the current system time, THE Provider_Adapter SHALL return the persisted access token and SHALL send no refresh exchange request.
4. WHILE a Grocery_Provider declares an Authentication_Capability of `oauth2_authorization_code` AND that provider's Connection_State is `connected`, WHEN a valid access token for that provider is requested and the persisted access token expiry of that provider is 60 seconds or less after the current system time, or no access token is persisted for that provider, THE Provider_Adapter SHALL exchange the persisted refresh token of that provider for a new access token before returning an access token.
5. WHEN a refresh exchange succeeds, THE Provider_Adapter SHALL persist the returned access token together with the absolute time at which that access token expires, computed from the expiry duration carried by the provider response, before returning that access token, and SHALL persist a returned refresh token in place of the refresh token previously persisted for that provider.
6. IF a refresh exchange succeeds and the provider response omits a refresh token, THEN THE Provider_Adapter SHALL retain the refresh token previously persisted for that provider and SHALL leave that provider's Connection_State as `connected`.
7. IF a Grocery_Provider rejects a refresh exchange because the persisted refresh token is invalid, expired, or revoked, THEN THE Provider_Adapter SHALL set that provider's Connection_State to `reauth_required`, SHALL return no access token, SHALL leave the Connection_State of every other provider unchanged, and SHALL return an error identifying that reauthorization of that provider is needed.
8. IF a Grocery_Provider rejects a refresh exchange for a reason other than an invalid, expired, or revoked refresh token, or the refresh exchange is abandoned without a response, THEN THE Provider_Adapter SHALL leave that provider's Connection_State as `connected`, SHALL leave that provider's persisted access token, refresh token, and access token expiry unchanged, and SHALL return an error identifying the refresh failure.
9. WHILE a refresh exchange for one Grocery_Provider is in progress, WHEN an access token for that provider is requested by any caller, THE Provider_Adapter SHALL send no additional refresh exchange request for that provider and SHALL return the access token produced by the in-progress exchange to every waiting caller, so that two concurrent token requests for one provider cause exactly one refresh exchange.
10. WHILE a Grocery_Provider's Connection_State is `reauth_required` or `disconnected`, IF an access token for that provider is requested, THEN THE Provider_Adapter SHALL send no request to that provider, SHALL return no access token, and SHALL return an error identifying that a connection to that provider is required.

### Requirement 4: Report and Reset Connection State per Provider

**User Story:** As the pantry owner, I want to see and change the connection state of each grocery provider independently, so that I know why provisioning to one provider is unavailable and can unlink that provider without disturbing another.

#### Acceptance Criteria

1. WHEN a client requests the connection status of the registered Grocery_Providers, THE Pantry SHALL return, within 1 second, for every registered provider, that provider's Provider_Identifier, exactly one of the four Connection_State values `not_required`, `connected`, `reauth_required`, or `disconnected`, and a single true-or-false indication of whether that provider is Credentials_Configured, reflecting that provider's Provider_Connection_Record at the time of the request.
2. IF no Provider_Connection_Record exists for a registered Grocery_Provider whose Authentication_Capability is other than `none` when a client requests connection status, THEN THE Pantry SHALL return a Connection_State of `disconnected` for that provider together with the current indication of whether that provider is Credentials_Configured.
3. WHEN a client requests disconnection of one named Grocery_Provider, THE Pantry SHALL remove the access token and the refresh token from that provider's Provider_Connection_Record, SHALL set that provider's Connection_State to `disconnected`, SHALL leave every Fulfillment_Ledger_Entry unchanged, SHALL leave the Provider_Connection_Record of every other provider unchanged, and SHALL return the resulting Connection_State of the named provider, regardless of whether credentials were stored for that provider before the request.
4. WHILE a Grocery_Provider's Connection_State is `disconnected` AND that provider is Credentials_Configured, THE Shopping_List_Page SHALL display a control that starts that provider's connection flow and SHALL display the provisioning control for that provider in a disabled state.
5. WHILE a Grocery_Provider's Connection_State is `reauth_required`, THE Shopping_List_Page SHALL display a message identifying that the connection to that provider expired, a control that restarts that provider's connection flow, and the provisioning control for that provider in a disabled state.
6. WHILE a Grocery_Provider's Connection_State is `connected` or `not_required` AND that provider is Credentials_Configured AND no In_Progress_Provision_Operation exists for that provider, IF the shopping list holds at least one Shopping_List_Entry whose Provision_Quantity for that provider is 1 or greater, THEN THE Shopping_List_Page SHALL display the provisioning control for that provider in an enabled state.
7. WHILE a Grocery_Provider's Connection_State is `connected` or `not_required`, IF the shopping list holds zero Shopping_List_Entries whose Provision_Quantity for that provider is 1 or greater, THEN THE Shopping_List_Page SHALL display the provisioning control for that provider in a disabled state.
8. WHILE a Grocery_Provider's Connection_State is `connected`, THE Shopping_List_Page SHALL display a control that requests disconnection of that provider.
9. WHEN the Connection_State of one Grocery_Provider changes, THE Pantry SHALL leave the Connection_State of every other registered Grocery_Provider unchanged.

### Requirement 5: Resolve Provider Product Identities

**User Story:** As the pantry owner, I want Pantry to work out each provider's own product identifier from the data it already holds, so that the right products are requested without a catalog call whenever the identifier can be derived from a barcode Pantry already stores.

#### Acceptance Criteria

1. WHEN a Provision_Operation begins, THE Provisioning_Engine SHALL request a Provider_Product_Identity from the Target_Provider's Provider_Adapter for every Shopping_List_Entry of the current shopping list read whose Provision_Quantity is 1 or greater, processing the entries one at a time in the order the shopping list returned them and regardless of whether an entry's source is `auto` or `manual`.
2. WHERE the Target_Provider declares a Product_Identity_Capability of `derived`, WHEN the Provisioning_Engine requests a Provider_Product_Identity, THE Provider_Adapter SHALL derive that identity from a barcode of the entry's pantry product and SHALL send no request to the Target_Provider or to any other external service while deriving that identity.
3. WHERE the Target_Provider declares a Product_Identity_Capability of `looked_up`, WHEN the Provisioning_Engine requests a Provider_Product_Identity, THE Provider_Adapter SHALL obtain that identity by calling the Target_Provider's product lookup operation with a barcode of the entry's pantry product.
4. WHEN a Provider_Adapter returns a Provider_Product_Identity for a Shopping_List_Entry, THE Provisioning_Engine SHALL produce a Resolved_Item carrying that Provider_Product_Identity together with that entry's Provision_Quantity unchanged.
5. IF a Provider_Adapter returns no Provider_Product_Identity for a Shopping_List_Entry, THEN THE Provisioning_Engine SHALL classify that entry as an Unresolved_Item and SHALL submit no Provision_Line accounting for that entry.
6. IF a Shopping_List_Entry's pantry product has no associated barcode, THEN THE Provisioning_Engine SHALL classify that entry as an Unresolved_Item and SHALL request no Provider_Product_Identity for that entry.
7. IF a Shopping_List_Entry carries a Provision_Quantity other than 0 that is not an integer between 1 and 999 inclusive, THEN THE Provisioning_Engine SHALL classify that entry as an Unresolved_Item and SHALL request no Provider_Product_Identity for that entry.
8. WHEN a pantry product carries more than one barcode, THE Provisioning_Engine SHALL present the barcodes of that product to the Provider_Adapter in ascending lexicographic order of barcode value and SHALL use the first Provider_Product_Identity returned in that order, so that two resolutions over the same set of barcode values produce the same Provider_Product_Identity.
9. WHERE a Shopping_List_Entry carries a Provision_Quantity of 0, THE Provisioning_Engine SHALL request no Provider_Product_Identity for that entry and SHALL classify that entry as neither a Resolved_Item nor an Unresolved_Item, so that a Provision_Quantity of 0 excludes the entry from the Provision_Operation rather than reporting that entry as unresolved.
10. WHEN identity resolution for a Provision_Operation completes, THE Provisioning_Engine SHALL have classified each Shopping_List_Entry whose Provision_Quantity is 1 or greater as exactly one of a Resolved_Item or an Unresolved_Item, producing one classification per such entry even when two entries resolve to the same Provider_Product_Identity.
11. IF a product lookup call to a Grocery_Provider whose Product_Identity_Capability is `looked_up` returns an error or is abandoned, THEN THE Provisioning_Engine SHALL classify the Shopping_List_Entry of that lookup as an Unresolved_Item and SHALL continue resolving the remaining entries of that Provision_Operation.
12. THE Pantry SHALL store the barcodes of a pantry product exactly as those barcodes were captured from the real-world object, and WHEN a Provider_Adapter resolves a Provider_Product_Identity for a Shopping_List_Entry, THE Pantry SHALL resolve that Provider_Product_Identity within the Provision_Operation that requested it, SHALL retain that Provider_Product_Identity no longer than that Provision_Operation, and SHALL persist no Provider_Product_Identity as a barcode of any pantry product, so that no stored barcode of any pantry product is ever a provider-specific value.

### Requirement 6: Choose a Replenishment Mode per Product

**User Story:** As the pantry owner, I want to choose for each product whether Pantry buys back what I consumed or tops the product up to its target supply, so that staples and occasional purchases are each restocked the way that suits them.

#### Acceptance Criteria

1. THE Pantry SHALL hold, for every pantry product, a Replenishment_Mode equal to exactly one of `target` or `replenish`.
2. WHERE no Replenishment_Mode has been recorded for a pantry product, THE Pantry SHALL treat that product's Replenishment_Mode as `target`, so that a product whose Replenishment_Mode has never been set yields the Computed_Quantity it yielded before Replenishment_Mode existed.
3. WHEN the pantry owner sets the Replenishment_Mode of a pantry product to `target` or to `replenish`, THE Pantry SHALL record that Replenishment_Mode against that pantry product alone and SHALL leave the Replenishment_Mode of every other pantry product unchanged.
4. THE Pantry SHALL hold one Replenishment_Mode per pantry product that applies to every registered Grocery_Provider, so that the mode of a product is independent of which provider is the Target_Provider.
5. WHEN the Pantry records a Replenishment_Mode for a pantry product, THE Pantry SHALL apply that Replenishment_Mode to the next computation of that product's Computed_Quantity and SHALL leave the Provision_Quantities of an In_Progress_Provision_Operation unchanged.
6. WHEN the Pantry records a Replenishment_Mode for a pantry product, THE Pantry SHALL retain the inventory instances, the consumption events, the target quantity, and every Fulfillment_Ledger_Entry of that pantry product unchanged.
7. WHEN the pantry owner sets the Replenishment_Mode of a pantry product that has no Shopping_List_Entry, THE Pantry SHALL record that Replenishment_Mode and SHALL apply that mode at the next computation of that product's Computed_Quantity.
8. IF a request sets a Replenishment_Mode to a value other than `target` or `replenish`, THEN THE Pantry SHALL leave the recorded Replenishment_Mode of every pantry product unchanged and SHALL return an error identifying the rejected value.
9. WHEN a client reads the shopping list, THE Pantry SHALL return, for every Shopping_List_Entry, the Replenishment_Mode of that entry's pantry product.
10. WHILE the Shopping_List_Page displays a Shopping_List_Entry, THE Shopping_List_Page SHALL display a control that sets the Replenishment_Mode of that entry's pantry product to `target` or to `replenish`.

### Requirement 7: Compute Provision Quantities

**User Story:** As the pantry owner, I want each quantity to follow that product's chosen mode and to subtract what Pantry already asked that provider for, so that asking twice does not double an order and each provider is accounted for on its own.

#### Acceptance Criteria

1. WHILE a pantry product's Replenishment_Mode is `target`, WHEN the Pantry computes the shopping list for a Target_Provider, THE Pantry SHALL set that product's Computed_Quantity to the greater of 0 and the target quantity recorded for that product minus the count of inventory instances currently held for that product minus the Requested_Quantity of the pair of that Target_Provider and that product.
2. WHILE a pantry product's Replenishment_Mode is `replenish`, WHEN the Pantry computes the shopping list for a Target_Provider, THE Pantry SHALL set that product's Computed_Quantity to the greater of 0 and the Consumed_Units of the pair of that Target_Provider and that product minus the Requested_Quantity of that pair.
3. WHEN the Pantry computes a Computed_Quantity for a Target_Provider, THE Pantry SHALL read the Requested_Quantity and the Ledger_Boundary of the Fulfillment_Ledger_Entry keyed by that Target_Provider and that pantry product alone, so that a Computed_Quantity for one provider is unaffected by what Pantry has requested from another provider.
4. IF the Computed_Quantity of a pantry product for a Target_Provider is 0, THEN THE Pantry SHALL omit that pantry product from the shopping list returned for that Target_Provider.
5. WHILE a pantry product's Replenishment_Mode is `target`, IF no target quantity is recorded for that product, THEN THE Pantry SHALL omit that product from the shopping list, preserving the behavior that a product without a target quantity is never provisioned in `target` mode.
6. WHILE a pantry product's Replenishment_Mode is `replenish`, WHERE no target quantity is recorded for that product, THE Pantry SHALL include that product in the shopping list with the Computed_Quantity of criterion 2 whenever that quantity is 1 or greater, so that a product carrying no target quantity reaches a provider in `replenish` mode although that product never does in `target` mode.
7. WHEN the Pantry computes the Consumed_Units of a pantry product for a Target_Provider, THE Pantry SHALL count the consumption events recorded for that product whose consumption time falls after the Ledger_Boundary of the pair of that Target_Provider and that product, counting one unit per consumption event.
8. WHERE no Fulfillment_Ledger_Entry exists for the pair of a Target_Provider and a pantry product, WHEN the Pantry computes the Consumed_Units of that pair, THE Pantry SHALL count every consumption event recorded for that pantry product, and SHALL apply a Requested_Quantity of 0 for that pair.
9. WHEN the Pantry computes a Computed_Quantity, THE Pantry SHALL retain every consumption event, every inventory instance, every target quantity, and every Fulfillment_Ledger_Entry unchanged.
10. WHEN a Shopping_List_Entry whose source is `manual` exists for a pantry product, THE Pantry SHALL set that entry's Computed_Quantity to the quantity recorded with that manual entry regardless of that pantry product's Replenishment_Mode and regardless of the Fulfillment_Ledger.
11. WHEN a client reads the shopping list for a Target_Provider, THE Pantry SHALL return, for every Shopping_List_Entry, the Computed_Quantity of that entry together with the basis of that Computed_Quantity, being the target quantity and the inventory instance count under a Replenishment_Mode of `target` and the Consumed_Units counted after the Ledger_Boundary under a Replenishment_Mode of `replenish`, together with the Requested_Quantity subtracted from that basis.
12. WHEN a client reads the shopping list without naming a Target_Provider and exactly one registered Grocery_Provider is Credentials_Configured, THE Pantry SHALL compute the shopping list for that provider and SHALL return the Provider_Identifier of that provider with the response.

### Requirement 8: Adjust Quantities Before Provisioning

**User Story:** As the pantry owner, I want to change any quantity before Pantry sends it to a provider, so that a single unusual week does not force me to edit targets or accept the wrong amount.

#### Acceptance Criteria

1. WHILE the Shopping_List_Page displays a Shopping_List_Entry, THE Shopping_List_Page SHALL display that entry's Computed_Quantity, the Replenishment_Mode that produced that Computed_Quantity, the basis of that Computed_Quantity as returned under Requirement 7, and the Provider_Identifier of the Target_Provider for which that Computed_Quantity was computed.
2. WHEN the pantry owner sets an Adjusted_Quantity on a Shopping_List_Entry for a named Target_Provider to an integer between 0 and 999 inclusive, THE Pantry SHALL record that Adjusted_Quantity against the pair of that Shopping_List_Entry and that Target_Provider alone, and SHALL leave the Adjusted_Quantity recorded against that entry for every other provider unchanged.
3. WHERE a Shopping_List_Entry carries an Adjusted_Quantity recorded for the Target_Provider, THE Pantry SHALL set that entry's Provision_Quantity to that Adjusted_Quantity, taking precedence over that entry's Computed_Quantity.
4. WHERE a Shopping_List_Entry carries no Adjusted_Quantity recorded for the Target_Provider, THE Pantry SHALL set that entry's Provision_Quantity to that entry's Computed_Quantity for that Target_Provider.
5. WHERE a Shopping_List_Entry carries an Adjusted_Quantity of 0 for the Target_Provider, THE Pantry SHALL exclude that entry from the Provision_Operation against that provider and SHALL submit no Provision_Line accounting for that entry.
6. WHEN the Pantry records an Adjusted_Quantity against a Shopping_List_Entry, THE Pantry SHALL retain the target quantity, the inventory instances, the consumption events, the Replenishment_Mode, and every Fulfillment_Ledger_Entry of that entry's pantry product unchanged.
7. IF a request sets an Adjusted_Quantity to a value that is not an integer between 0 and 999 inclusive, THEN THE Pantry SHALL leave the recorded Adjusted_Quantity of every Shopping_List_Entry unchanged and SHALL return an error identifying the rejected value.
8. WHILE a Shopping_List_Entry carries an Adjusted_Quantity recorded for one Target_Provider and no Provision_Operation against that provider has recorded a Provision_Outcome of `confirmed` for that entry, THE Pantry SHALL return that Adjusted_Quantity on every read of the shopping list for that provider.
9. WHEN a Provision_Operation records a Provision_Outcome of `confirmed` for a Shopping_List_Entry, THE Pantry SHALL discard the Adjusted_Quantity recorded against the pair of that entry and that Target_Provider, so that the next read of the shopping list for that provider returns that entry's Provision_Quantity as its freshly computed Computed_Quantity.
10. WHEN a Provision_Operation records a Provision_Outcome of `failed` or `unknown` for a Shopping_List_Entry, THE Pantry SHALL retain the Adjusted_Quantity recorded against the pair of that entry and that Target_Provider.
11. WHILE the Shopping_List_Page displays a Shopping_List_Entry carrying an Adjusted_Quantity recorded for the Target_Provider, THE Shopping_List_Page SHALL display that Adjusted_Quantity as the Provision_Quantity together with the Computed_Quantity that Adjusted_Quantity replaces.
12. WHEN the pantry owner removes an Adjusted_Quantity recorded against a Shopping_List_Entry for a Target_Provider, THE Pantry SHALL set that entry's Provision_Quantity to that entry's Computed_Quantity for that provider on the next read of the shopping list.

### Requirement 9: Submit Provision Requests to a Provider

**User Story:** As the pantry owner, I want my shopping list handed to the chosen grocery provider in one action, so that I can open that provider's app and check out immediately.

#### Acceptance Criteria

1. WHILE the Target_Provider declares a Delivery_Capability of `server_push` AND that provider's Connection_State is `connected` or `not_required`, WHEN a Provision_Operation runs, THE Provisioning_Engine SHALL submit a Provision_Line for every Resolved_Item to that provider, sending at most that provider's Provision_Batch_Size Provision_Lines per Provision_Request and submitting further Provision_Requests sequentially until every Resolved_Item has been accounted for by a submitted Provision_Line.
2. WHERE the Target_Provider declares a Delivery_Capability of `client_handoff`, WHEN a Provision_Operation runs, THE Provisioning_Engine SHALL produce a Handoff_Artifact carrying a Provision_Line for every Resolved_Item, SHALL return that Handoff_Artifact, and SHALL send no Provision_Request to that provider.
3. WHEN the Provisioning_Engine reads the Provision_Batch_Size of a Grocery_Provider, THE Provisioning_Engine SHALL read the policy value held for that provider alone, so that two registered providers can carry different Provision_Batch_Size values.
4. WHEN two or more Resolved_Items of one Provision_Operation carry the same Provider_Product_Identity, THE Provisioning_Engine SHALL submit exactly one Provision_Line for that Provider_Product_Identity carrying the sum of those Resolved_Items' Provision_Quantities constrained to a maximum of 999.
5. WHEN the Provisioning_Engine submits a Provision_Line, THE Provisioning_Engine SHALL send a quantity derived from the Provision_Quantity of every Resolved_Item accounted for by that Provision_Line, constrained to the range 1 to 999 inclusive.
6. IF a Grocery_Provider rejects a Provision_Request, THEN THE Provisioning_Engine SHALL record a Provision_Outcome of `failed` for every Shopping_List_Entry accounted for by that Provision_Request and SHALL continue submitting the remaining Provision_Requests of that Provision_Operation.
7. IF a Provision_Operation produces zero Resolved_Items, THEN THE Provisioning_Engine SHALL send no Provision_Request, SHALL produce no Handoff_Artifact, and SHALL report a count of zero items confirmed.
8. IF the Connection_State of the Target_Provider is `disconnected` or `reauth_required` when a Provision_Operation runs, THEN THE Provisioning_Engine SHALL send no request to that provider, SHALL leave every Fulfillment_Ledger_Entry unchanged, and SHALL return an error identifying that a connection to that provider is required.
9. IF a Provider_Adapter returns an error while a Provision_Operation is obtaining a credential for the Target_Provider, THEN THE Provisioning_Engine SHALL send no further Provision_Request for that Provision_Operation, SHALL record a Provision_Outcome of `failed` for every Shopping_List_Entry not yet accounted for by a confirmed Provision_Request, and SHALL return a response identifying that a valid credential for that provider could not be obtained.
10. IF a Provision_Operation against one Target_Provider is requested while an In_Progress_Provision_Operation against that same provider exists, THEN THE Pantry SHALL send no request to that provider for the later Provision_Operation and SHALL return an error identifying that a Provision_Operation against that provider is already in progress.
11. WHERE the Target_Provider declares a Mutation_Capability of `add_only`, WHEN a Provision_Operation runs, THE Provisioning_Engine SHALL invoke only that provider's add operation and SHALL invoke no read, update, or removal operation of that provider.
12. WHEN a Provision_Operation against one Target_Provider runs, THE Provisioning_Engine SHALL send no request to any Grocery_Provider other than that Target_Provider.

### Requirement 10: Maintain the Fulfillment Ledger Idempotently

**User Story:** As the pantry owner, I want Pantry to remember exactly what it has already asked each provider for, so that asking again does not double my order, a failure never erases what I still need, and starting a new cart puts Pantry back in step with reality.

#### Acceptance Criteria

1. WHEN a Provision_Operation records a Provision_Outcome of `confirmed` for a Shopping_List_Entry carrying a Provision_Quantity, THE Provisioning_Engine SHALL increase the Requested_Quantity of the Fulfillment_Ledger_Entry keyed by the Target_Provider and that entry's pantry product by that Provision_Quantity, creating that Fulfillment_Ledger_Entry where none exists.
2. IF a Provision_Operation records a Provision_Outcome of `failed` or `unknown` for a Shopping_List_Entry, THEN THE Provisioning_Engine SHALL leave the Requested_Quantity and the Ledger_Boundary of the Fulfillment_Ledger_Entry keyed by the Target_Provider and that entry's pantry product unchanged.
3. WHEN a Provision_Operation records a Provision_Outcome of `confirmed` for a Shopping_List_Entry, THE Provisioning_Engine SHALL leave the Ledger_Boundary of that Fulfillment_Ledger_Entry unchanged, so that a confirmation advances what Pantry believes it has requested without erasing the basis from which that belief is measured.
4. WHEN a Provision_Operation updates a Fulfillment_Ledger_Entry, THE Provisioning_Engine SHALL leave every Fulfillment_Ledger_Entry keyed by a Grocery_Provider other than the Target_Provider unchanged, so that requesting a pantry product from one provider leaves what Pantry believes about every other provider unchanged.
5. WHEN a Provision_Operation updates a Fulfillment_Ledger_Entry, THE Provisioning_Engine SHALL leave every Fulfillment_Ledger_Entry keyed by a pantry product other than that of the confirmed Shopping_List_Entry unchanged.
6. WHEN an inventory instance of a pantry product is stocked in, THE Pantry SHALL set the Requested_Quantity of every Fulfillment_Ledger_Entry keyed by that pantry product to 0 and SHALL set the Ledger_Boundary of every such entry to the time of that stock-in, so that evidence of purchase clears what Pantry believes it has outstanding for that product.
7. WHEN the pantry owner requests a ledger reset for one named Grocery_Provider, THE Pantry SHALL set the Requested_Quantity of every Fulfillment_Ledger_Entry keyed by that provider to 0, SHALL set the Ledger_Boundary of every such entry to the time of that request, SHALL leave every Fulfillment_Ledger_Entry keyed by another provider unchanged, and SHALL leave every inventory instance, consumption event, and target quantity unchanged.
8. WHILE a Grocery_Provider is registered, THE Shopping_List_Page SHALL display a control that requests a ledger reset for that provider, labelled as indicating that a new cart was started or that the previous cart was checked out.
9. WHEN a Provision_Operation runs a second time against one Target_Provider while every inventory instance, consumption event, target quantity, and Replenishment_Mode is unchanged since the first Provision_Operation confirmed every Shopping_List_Entry, THE Pantry SHALL compute a Provision_Quantity of 0 for every pantry product confirmed by the first Provision_Operation, so that the second Provision_Operation submits no Provision_Line for those products under either Replenishment_Mode.
10. WHEN the Pantry computes a Provision_Quantity, THE Pantry SHALL compute an integer of 0 or greater for every combination of target quantity, inventory instance count, Consumed_Units, and Requested_Quantity.
11. WHEN a client requests the Fulfillment_Ledger of one named Grocery_Provider, THE Pantry SHALL return, for every Fulfillment_Ledger_Entry keyed by that provider, the pantry product of that entry, the Requested_Quantity of that entry, and the Ledger_Boundary of that entry as an absolute UTC timestamp with a precision of one second or finer.
12. WHEN the Pantry persists a Fulfillment_Ledger_Entry, THE Pantry SHALL persist that entry keyed by the pair of a Provider_Identifier and a pantry product, so that exactly one Fulfillment_Ledger_Entry exists per such pair.

### Requirement 11: Report Outcomes Including Unknown

**User Story:** As the pantry owner, I want to know which items reached the provider, which did not, and which Pantry cannot tell, so that I can buy the rest another way and decide for myself what to do about an indeterminate result.

#### Acceptance Criteria

1. WHEN a Provision_Operation completes, THE Pantry SHALL record, for every Shopping_List_Entry whose Provision_Quantity was 1 or greater, exactly one Provision_Outcome equal to `confirmed`, `failed`, or `unknown`.
2. WHERE the Target_Provider declares a Confirmation_Capability of `per_line`, WHEN a Provision_Request completes, THE Provisioning_Engine SHALL record the Provision_Outcome of each Shopping_List_Entry from the provider-reported result of the Provision_Line accounting for that entry.
3. WHERE the Target_Provider declares a Confirmation_Capability of `per_request`, WHEN a Provision_Request completes, THE Provisioning_Engine SHALL record the same Provision_Outcome for every Shopping_List_Entry accounted for by that Provision_Request, being `confirmed` where the provider accepted that Provision_Request and `failed` where the provider rejected that Provision_Request.
4. WHERE the Target_Provider declares a Confirmation_Capability of `none`, WHEN a Provision_Request completes, THE Provisioning_Engine SHALL record a Provision_Outcome of `unknown` for every Shopping_List_Entry accounted for by that Provision_Request.
5. IF a Provision_Request is abandoned at that provider's attempt limit, or completes with a result from which acceptance and rejection cannot be distinguished, THEN THE Provisioning_Engine SHALL record a Provision_Outcome of `unknown` for every Shopping_List_Entry accounted for by that Provision_Request.
6. WHERE the Target_Provider declares a Delivery_Capability of `client_handoff`, WHEN a Handoff_Artifact is returned, THE Provisioning_Engine SHALL record a Provision_Outcome of `unknown` for every Shopping_List_Entry carried by that Handoff_Artifact.
7. WHEN a Provision_Operation completes, THE Pantry SHALL return the count of Shopping_List_Entries whose Provision_Outcome is `confirmed`, and SHALL return, for every Shopping_List_Entry whose Provision_Outcome is `failed` or `unknown`, the pantry product name of that entry, that Provision_Outcome, and exactly one reason: no Provider_Product_Identity could be resolved for the entry, the provider rejected the request accounting for the entry, the request accounting for the entry could not be completed, or the provider reports no per-item result.
8. WHEN a Provision_Operation completes, THE Pantry SHALL retain every Shopping_List_Entry that existed before that Provision_Operation began, each with the pantry item identifier, source, purchased state, target quantity, and Replenishment_Mode it held before that Provision_Operation began.
9. WHEN a Provision_Operation returns at least one Shopping_List_Entry whose Provision_Outcome is `failed`, THE Shopping_List_Page SHALL display the pantry product name of every such entry, up to a maximum of 50 names plus a count of any names beyond 50, together with a statement that those items remain on the shopping list, and SHALL keep that display visible until the next Provision_Operation against that provider begins or the page is reloaded.
10. WHEN a Provision_Operation returns at least one Shopping_List_Entry whose Provision_Outcome is `unknown`, THE Shopping_List_Page SHALL display the pantry product name of every such entry together with a control that records the pantry owner's explicit confirmation that those units reached that provider and a control that records that those units did not reach that provider.
11. WHEN the pantry owner records explicit confirmation that the units of a Shopping_List_Entry whose Provision_Outcome is `unknown` reached a Grocery_Provider, THE Pantry SHALL increase the Requested_Quantity of the Fulfillment_Ledger_Entry keyed by that provider and that entry's pantry product by the Provision_Quantity of that entry and SHALL discard the Adjusted_Quantity recorded against the pair of that entry and that provider.
12. WHEN the pantry owner records that the units of a Shopping_List_Entry whose Provision_Outcome is `unknown` did not reach a Grocery_Provider, THE Pantry SHALL leave every Fulfillment_Ledger_Entry unchanged and SHALL retain the Adjusted_Quantity recorded against the pair of that entry and that provider.
13. WHEN a Provision_Operation returns zero Shopping_List_Entries whose Provision_Outcome is `failed` or `unknown`, THE Shopping_List_Page SHALL display the count of confirmed items exactly as returned by that Provision_Operation, and SHALL keep that display visible until the next Provision_Operation against that provider begins or the page is reloaded.
14. IF a Provision_Operation returns an error in place of a provisioning outcome, THEN THE Shopping_List_Page SHALL display an error message identifying the returned reason, SHALL display no confirmed-item count, and SHALL leave every displayed Shopping_List_Entry unchanged.
15. WHILE an In_Progress_Provision_Operation exists for one Grocery_Provider, THE Shopping_List_Page SHALL display the provisioning control for that provider in a disabled state together with an in-progress indicator until that Provision_Operation returns an outcome or an error.

### Requirement 12: Configure Providers Through the Environment

**User Story:** As the operator of the Pi deployment, I want to supply each provider's credentials through environment variables and switch any single provider off, so that I can run Pantry locally and deploy it without code changes and without one misconfigured provider taking the others down.

#### Acceptance Criteria

1. WHEN the Pantry starts, THE Pantry SHALL read, for every registered Grocery_Provider, the Provider_Credentials values that provider's Authentication_Capability requires from environment variables namespaced by that provider's Provider_Identifier, before the Pantry begins serving requests, discarding leading and trailing whitespace from each value and treating a value that is unset or that holds only whitespace as absent.
2. WHERE any Provider_Credentials value required by a Grocery_Provider's Authentication_Capability is absent, THE Pantry SHALL report that provider as not Credentials_Configured, SHALL report a Connection_State of `disconnected` for that provider, SHALL log the absent value name, and SHALL leave every other registered Grocery_Provider available for a Provision_Operation.
3. WHERE the environment variable that disables one named Grocery_Provider is set to `true`, THE Pantry SHALL report that provider as not Credentials_Configured and SHALL leave every other registered Grocery_Provider available for a Provision_Operation, and WHERE that variable is unset or holds any other value, THE Pantry SHALL treat that provider as enabled.
4. WHERE no registered Grocery_Provider is Credentials_Configured, THE Pantry SHALL wire the existing no-op cart exporter and SHALL report every registered provider as not Credentials_Configured.
5. WHEN the Pantry starts, THE Pantry SHALL read the optional Provision_Batch_Size of every registered Grocery_Provider from an environment variable namespaced by that provider's Provider_Identifier, and WHERE that value is absent or is not an integer between 1 and 50 inclusive, THE Pantry SHALL apply a Provision_Batch_Size of 50 for that provider.
6. WHEN the Pantry starts, THE Pantry SHALL read the optional provider-specific line options of every registered Grocery_Provider from environment variables namespaced by that provider's Provider_Identifier.
7. IF a provider-specific option value read from the environment is outside the values that option permits, THEN THE Pantry SHALL log the rejected value, SHALL apply that option's default value, SHALL continue startup to the point of serving requests, and SHALL continue to report that provider as Credentials_Configured whenever every required Provider_Credentials value of that provider is present.
8. WHILE a Grocery_Provider is not Credentials_Configured, THE Shopping_List_Page SHALL display the provisioning control for that provider in a disabled state together with a statement that the named provider is unconfigured, and SHALL start no Provision_Operation against that provider.
9. IF a Provision_Operation runs against a Grocery_Provider that is not Credentials_Configured, THEN THE Pantry SHALL send no request to that provider, SHALL leave every Shopping_List_Entry and every Fulfillment_Ledger_Entry unchanged, and SHALL return an error identifying that the named provider is unconfigured.
10. IF any environment value of any Grocery_Provider is absent or invalid, THEN THE Pantry SHALL complete startup and serve requests rather than terminating, and SHALL keep every Pantry capability unrelated to grocery provisioning available.

### Requirement 13: Survive Provider Latency and Rate Limits

**User Story:** As the pantry owner, I want a slow or throttled provider to produce a clear result rather than a hung page, so that I know whether to retry.

The 10-second attempt limit, the 3-attempt cap, and the 500-millisecond and 1000-millisecond waits stated below are Pantry's own per-provider timeout and backoff policy. They are not limits published by any Grocery_Provider. Each registered Grocery_Provider carries its own values for these policy settings, defaulting to the values stated here.

#### Acceptance Criteria

1. IF no complete response to a request attempt against a Grocery_Provider arrives within that provider's attempt limit of 10 seconds, THEN THE Provider_Adapter SHALL abandon that attempt and SHALL apply that same attempt limit independently to each further attempt of the same request, so that a single request for which that provider supplies no retry-after indication occupies at most 31.5 seconds across all attempts.
2. IF a Grocery_Provider responds to a request attempt with a rate-limit status or a server-error status, THEN THE Provider_Adapter SHALL retry that request at most 2 further times, waiting 500 milliseconds after the end of the first attempt before the first retry and 1000 milliseconds after the end of the second attempt before the second retry.
3. IF a Grocery_Provider responds with a rate-limit status or a server-error status on all 3 attempts of a request, THEN THE Provider_Adapter SHALL send no further attempt for that request and SHALL return an error identifying the provider status of the third attempt.
4. IF a Grocery_Provider responds with a client-error status other than a rate-limit status, THEN THE Provider_Adapter SHALL send no further attempt for that request and SHALL return an error identifying that provider status.
5. WHERE a Grocery_Provider supplies a retry-after indication on a rate-limit response, THE Provider_Adapter SHALL wait at least the duration carried by that indication, measured from the end of the attempt that received the response, before sending the next attempt of that request.
6. IF a credential request attempt against a Grocery_Provider is abandoned at that provider's attempt limit, THEN THE Provider_Adapter SHALL retry that request subject to the same attempt count and wait durations that apply to a rate-limit status.
7. IF a Provision_Request attempt against a Grocery_Provider whose Mutation_Capability is `add_only` is abandoned at that provider's attempt limit, THEN THE Provider_Adapter SHALL send no further attempt for that Provision_Request and SHALL return a result identifying the timeout as indeterminate, so that no Provision_Line is submitted twice.
8. IF a Provision_Request of a Provision_Operation is abandoned at the attempt limit or returns an indeterminate result after its final attempt, THEN THE Provisioning_Engine SHALL record a Provision_Outcome of `unknown` for every Shopping_List_Entry accounted for by that Provision_Request, SHALL leave every Fulfillment_Ledger_Entry unchanged, and SHALL return the Provision_Operation response carrying the confirmed count and every `failed` and `unknown` entry.
9. WHEN the Provider_Adapter of one Grocery_Provider applies a timeout or backoff policy value, THE Provider_Adapter SHALL apply the value held for that provider alone, so that a slow provider imposes no wait on a request to another provider.
10. WHILE a Provision_Operation against one Grocery_Provider is in flight, THE Shopping_List_Page SHALL display the provisioning control for that provider in a disabled state together with an in-progress indicator until that Provision_Operation returns a response or an error, at which point THE Shopping_List_Page SHALL re-enable that provisioning control and display either the Provision_Operation outcome or a message identifying that the request to that provider failed.

### Requirement 14: Keep Provider Credentials Server-Side

**User Story:** As the pantry owner, I want every provider credential confined to the server, so that linking a grocery account does not expose that account through the browser or the logs.

#### Acceptance Criteria

1. THE Pantry SHALL confine every access token value, refresh token value, API key value, and client secret value of every Grocery_Provider to that provider's Provider_Connection_Record, to process configuration read from the environment, and to outbound provider request headers and request bodies, and SHALL omit all such values from every response body, response header, and redirect URL that the Pantry returns to a frontend client.
2. WHEN a client requests the connection status of the registered Grocery_Providers, THE Pantry SHALL return, per provider, only the Provider_Identifier, the display name, the five declared capability values, the Connection_State, and whether that provider is Credentials_Configured, and SHALL omit every access token value, refresh token value, access token expiry time, API key value, client secret value, and Authorization_State value.
3. WHEN the Pantry logs a request to a Grocery_Provider or an error from a Grocery_Provider, THE Pantry SHALL write the Provider_Identifier, the request path, and the response status, and SHALL omit every access token value, refresh token value, API key value, client secret value, and authorization code value from that log entry.
4. IF a Grocery_Provider response body contains an access token value, a refresh token value, or an authorization code value, THEN THE Pantry SHALL omit that response body from log output and SHALL log the Provider_Identifier, the request path, and the response status instead.
5. IF the Pantry returns an error arising from an authorization code exchange, a refresh exchange, or a Provision_Request, THEN THE Pantry SHALL include in the client-visible error only the Provider_Identifier, the failure category, and the provider response status, and SHALL omit every access token value, refresh token value, API key value, client secret value, authorization code value, and provider response body.
6. WHEN a Grocery_Provider redirects to that provider's configured redirect URI and the Provider_Adapter finishes handling that callback, THE Pantry SHALL return a redirect to the Shopping_List_Page whose URL carries no authorization code value, access token value, or refresh token value.
7. WHERE a Grocery_Provider declares a Delivery_Capability of `client_handoff`, WHEN the Provisioning_Engine returns a Handoff_Artifact, THE Provisioning_Engine SHALL include in that Handoff_Artifact only Provider_Product_Identities, quantities, and provider-specific line options, and SHALL omit every credential value of that provider.

### Requirement 15: Exchange Well-Formed Payloads and Uphold Core Properties

**User Story:** As a developer, I want the provider-agnostic core guarded by universal properties, so that a quantity, ledger, or capability mistake surfaces in tests rather than as a doubled order or an item that silently vanishes from my shopping list.

#### Acceptance Criteria

1. WHEN the Provisioning_Engine presents a Provision_Request to a Provider_Adapter, THE Provisioning_Engine SHALL present between 1 Provision_Line and that provider's Provision_Batch_Size Provision_Lines, each Provision_Line carrying a non-empty Provider_Product_Identity, an integer quantity between 1 and 999 inclusive, and only those provider-specific line options that the Target_Provider declares.
2. IF a Provision_Request presented to a Provider_Adapter carries zero Provision_Lines, more Provision_Lines than that provider's Provision_Batch_Size, a Provision_Line quantity outside 1 to 999 inclusive, an empty Provider_Product_Identity, or a provider-specific line option that the Target_Provider does not declare, THEN THE Provisioning_Engine SHALL send no request to that provider and SHALL return an error identifying the rejected field.
3. IF a Grocery_Provider response body is not valid in the format that provider's Provider_Adapter declares, or is truncated before the end of that document, THEN THE Provider_Adapter SHALL return an error identifying the malformed response, SHALL return no deserialized payload, and SHALL leave every Provider_Connection_Record and every Fulfillment_Ledger_Entry unchanged.
4. FOR ALL Grocery_Providers whose Confirmation_Capability is other than `none`, and for all sets of Shopping_List_Entries, running a Provision_Operation against that provider twice while every inventory instance, consumption event, target quantity, and Replenishment_Mode is unchanged between the two Provision_Operations SHALL leave the total quantity requested from that provider for every pantry product equal to the total quantity that a single Provision_Operation requests (idempotence property).
5. FOR ALL Shopping_List_Entries whose Provision_Outcome in a Provision_Operation is `failed` or `unknown`, the Provision_Quantity that the next shopping list read computes for that entry's pantry product and that Target_Provider SHALL be greater than or equal to the Provision_Quantity computed for that pair immediately before that Provision_Operation began, given unchanged inventory instances, consumption events, target quantity, and Replenishment_Mode (no-loss property).
6. FOR ALL Grocery_Providers and for all Provisioning_Engine operations, every Provider_Adapter operation the Provisioning_Engine invokes SHALL be an operation that the Provider_Capabilities of that provider declare (capability-honesty property).
7. FOR ALL combinations of target quantity, inventory instance count, Consumed_Units, and Requested_Quantity, the Provision_Quantity the Pantry computes SHALL be an integer of 0 or greater (ledger non-negativity property).

### Requirement 16: Verify Every Provider Against a Shared Contract Suite

**User Story:** As a developer, I want one behavioral suite that every provider adapter must pass, running with no network and no credentials, so that the capability abstraction is proven on every pull request rather than only against the single live provider I happen to have credentials for.

#### Acceptance Criteria

1. THE Pantry SHALL hold exactly one Contract_Suite that every registered Provider_Adapter is verified against.
2. WHEN the Contract_Suite runs against one Provider_Adapter, THE Contract_Suite SHALL read that adapter's Provider_Capabilities and SHALL exercise the behavior that each declared capability value requires, so that one suite covers adapters declaring different capability values.
3. WHEN the Contract_Suite runs against one Provider_Adapter, THE Contract_Suite SHALL verify that the adapter implements every operation that adapter's Provider_Capabilities declare.
4. IF a Provider_Adapter is registered and the Contract_Suite has no case covering a capability value that adapter declares, THEN THE Contract_Suite SHALL fail with a message identifying that Provider_Identifier and that uncovered capability value.
5. THE Pantry test code SHALL hold a Fake_Provider whose five capability values are set per test case.
6. WHEN the Contract_Suite runs, THE Contract_Suite SHALL run against the Fake_Provider configured with a Confirmation_Capability of `none`, with a Mutation_Capability of `full`, with a Product_Identity_Capability of `looked_up`, and with a Delivery_Capability of `client_handoff`, so that capability values the Kroger_Adapter does not declare are covered.
7. WHEN the Contract_Suite runs, THE Contract_Suite SHALL complete every case without opening a network connection and without reading any Provider_Credentials value, so that the suite runs on every pull request including a pull request from a fork, for which the Pantry continuous integration workflow supplies no secrets.
8. WHEN the Contract_Suite runs against the Fake_Provider, THE Contract_Suite SHALL verify the idempotence property, the no-loss property, the capability-honesty property, and the ledger non-negativity property of Requirement 15 for every capability combination the suite configures.
9. WHERE a credentialed verification against a live Grocery_Provider is performed, THE Pantry SHALL run that verification as an activity separate from the Contract_Suite, and THE Pantry continuous integration workflow SHALL report a pull request result that is independent of whether that credentialed verification ran.

### Requirement 17: Kroger Provider Adapter

**User Story:** As the pantry owner, I want Kroger available as the first grocery provider, so that my shopping list reaches my own Kroger cart and I can check out in the Kroger app.

A captured Kroger product-search response shows `productId` and `upc` holding the same 13-digit value, so Kroger's product identifier is derived from the barcode Pantry already stores and needs no provider call ([captured response](https://github.com/jtbricker/python-kroger-client/blob/master/docs/api_responses/products.json)). The Kroger_Adapter therefore declares a Product_Identity_Capability of `derived`.

That shared value is **not** the zero-padded 12-digit UPC. It is the GTIN with its check digit discarded, left-padded with `0` characters to 13. The Kroger Products API documentation states that the identifier is the 13-digit `productId` and that the check digit is omitted when converting from a barcode, and the rule was confirmed arithmetically against four published Kroger identifiers — `0001111060903`, `0001111041700`, `0001200016268`, and `0001111041600`, the last being the identifier carried by the capture cited above — none of which is a valid zero-padded UPC-A or a valid EAN-13, and every one of which this rule reproduces.

Producing the wrong identifier is a silent fault rather than a loud one: Kroger validates only that the product identifier holds 13 characters, so a wrong-but-13-digit identifier is accepted and adds a different product to the cart without any error. The criteria below therefore specify both the derivation and the check-digit gate that guards it.

#### Acceptance Criteria

1. WHEN the Pantry starts, THE Provider_Registry SHALL register the Kroger_Provider with a Provider_Identifier of `kroger` and with Provider_Capabilities declaring an Authentication_Capability of `oauth2_authorization_code`, a Delivery_Capability of `server_push`, a Confirmation_Capability of `per_request`, a Mutation_Capability of `add_only`, and a Product_Identity_Capability of `derived`.
2. THE Kroger_Adapter SHALL declare an authorization scope of `cart.basic:write`, being the scope string the Kroger Cart API declares for write access to a customer's cart, and SHALL require a client identifier, a client secret, and a redirect URI as its Provider_Credentials.
3. WHEN the Kroger_Adapter resolves a Provider_Product_Identity, THE Kroger_Adapter SHALL return a Normalized_Barcode derived from a barcode of the pantry product and SHALL send no request to the Kroger Public API or to any other external service while deriving that value.
4. WHEN the Kroger_Adapter normalizes a barcode holding 12 digits, THE Kroger_Adapter SHALL validate the UPC-A check digit that barcode carries, SHALL discard that check digit, and SHALL left-pad the remaining 11 data digits with two `0` characters to produce a Normalized_Barcode, so that the barcode `011110728227` produces the Normalized_Barcode `0001111072822`.
5. WHEN the Kroger_Adapter normalizes a barcode holding 13 digits, THE Kroger_Adapter SHALL treat that barcode as an EAN-13, SHALL validate the check digit that barcode carries, SHALL discard that check digit, and SHALL left-pad the remaining 12 data digits with one `0` character to produce a Normalized_Barcode (this branch applies Kroger's documented conversion rule, for which Kroger publishes no worked example of a 13-digit barcode, so this branch is recorded as an open question on that narrower ground alone).
6. WHEN the Kroger_Adapter normalizes a barcode holding 8 digits, THE Kroger_Adapter SHALL expand that barcode into its GTIN-12 equivalent according to the UPC-E decoding table of the GS1 General Specifications section 5.2.2.4.2 (Table 5-7), SHALL validate the check digit the barcode carries against the check digit recomputed over the 11 data digits of that expanded GTIN-12, SHALL discard that check digit, and SHALL left-pad those 11 data digits with two `0` characters to produce a Normalized_Barcode.
7. IF the check digit a barcode carries disagrees with the check digit recomputed over that barcode's data digits, THEN THE Kroger_Adapter SHALL produce no Normalized_Barcode from that barcode and SHALL return no Provider_Product_Identity for that barcode, so that a misread barcode or a mistaken UPC-E expansion is rejected rather than normalized into the identifier of a different product that Kroger would accept unchallenged.
8. IF a barcode holds a digit count other than 8, 12, or 13, holds any character that is not a digit, or holds an empty string, THEN THE Kroger_Adapter SHALL produce no Normalized_Barcode from that barcode and SHALL return no Provider_Product_Identity for that barcode, so that the Provisioning_Engine classifies the Shopping_List_Entry as an Unresolved_Item under Requirement 5 once every barcode of that entry's pantry product has been presented with that outcome.
9. WHEN the Kroger_Adapter submits a Provision_Line and no Cart_Modality is configured for the Kroger_Provider, THE Kroger_Adapter SHALL send a Cart_Modality of `PICKUP`, and WHERE a Cart_Modality is configured for the Kroger_Provider, THE Kroger_Adapter SHALL send the configured Cart_Modality with every Provision_Line.
10. IF the configured Cart_Modality, compared without regard to letter case after whitespace is discarded, holds a value other than `PICKUP` or `DELIVERY`, THEN THE Pantry SHALL log the rejected value, SHALL apply a Cart_Modality of `PICKUP`, SHALL continue startup to the point of serving requests, and SHALL continue to report the Kroger_Provider as Credentials_Configured whenever the client identifier, the client secret, and the redirect URI are all present.
11. WHEN the Kroger_Adapter submits between 1 Provision_Line and the Kroger_Provider's Provision_Batch_Size Provision_Lines, THE Kroger_Adapter SHALL serialize a cart-add payload as JSON carrying exactly one `items` array, that array holding exactly one entry per Provision_Line, and each entry carrying the Normalized_Barcode in a field named `upc`, an integer `quantity` between 1 and 999 inclusive, and a `modality` of either `PICKUP` or `DELIVERY`.
12. IF a cart-add payload presented to the Kroger_Adapter for serialization carries a product identifier holding a character count other than 13 or holding any character that is not a digit, or a Cart_Modality other than `PICKUP` or `DELIVERY`, THEN THE Kroger_Adapter SHALL send no request to the Kroger Public API and SHALL return an error identifying the rejected payload field.
13. WHEN the Kroger Public API accepts a cart-add Provision_Request, THE Provisioning_Engine SHALL record a Provision_Outcome of `confirmed` for every Shopping_List_Entry accounted for by that Provision_Request, and WHEN the Kroger Public API rejects a cart-add Provision_Request, THE Provisioning_Engine SHALL record a Provision_Outcome of `failed` for every Shopping_List_Entry accounted for by that Provision_Request, including every entry whose own Provision_Line was well formed, because the Kroger Confirmation_Capability of `per_request` means Kroger reports one result for a whole Provision_Request rather than one result per Provision_Line.
14. FOR ALL valid Kroger cart-add payloads — a payload carrying 1 to the Kroger_Provider's Provision_Batch_Size Provision_Lines, each Provision_Line carrying a product identifier of exactly 13 digits, an integer quantity between 1 and 999 inclusive, and a Cart_Modality of either `PICKUP` or `DELIVERY` — serializing the payload to JSON and then deserializing that JSON SHALL produce a payload whose Provision_Line count, Provision_Line order, and per-Provision_Line product identifier, quantity, and Cart_Modality are equal to those of the original payload (round-trip property).
15. FOR ALL barcodes from which the Kroger_Adapter produces a Normalized_Barcode, that Normalized_Barcode SHALL hold exactly 13 characters and every one of those characters SHALL be a digit (invariant property).
16. FOR ALL valid GTINs, normalizing one GTIN twice SHALL produce the same Normalized_Barcode on both occasions, and FOR ALL pairs of different valid GTINs holding the same digit count, normalizing the two GTINs SHALL produce two different Normalized_Barcodes (determinism and injectivity property).
17. FOR ALL barcodes holding 12 digits from which the Kroger_Adapter produces a Normalized_Barcode, that Normalized_Barcode SHALL end with the first 11 of those digits in their original order (digit-preservation property).
18. WHERE a barcode holding 8 digits is ambiguous between a UPC-E and an EAN-8, THE Kroger_Adapter SHALL treat that barcode as a UPC-E whenever it begins with `0` and the check digit it carries agrees with the check digit recomputed over its expanded GTIN-12, and THE Pantry SHALL record no barcode scheme against a barcode of a pantry product, so that the residual misreading of an EAN-8 as a UPC-E is an accepted outcome of this feature rather than a defect to be resolved by a further gate or by a recorded scheme.
